# 碳迹未来使用与开发交接指南

这份指南面向第一次运行平台的人、日常运维人员和接手开发的工程师。先用本机 Docker 跑通校园浏览、核算、模拟控制和报告，再按需要阅读部署细节。

**交付默认状态：物理执行关闭。** 开发账户、设备、能源数据、故障和核算参数是明确标记的开发样例；空间参考来自固定版本的来源资产。界面、软件测试和模型都不代表真实校园已部署、硬件已通过强电检验或已实现节能。

## 1 Windows 首次启动

1. 安装并启动 Docker Desktop，使用 **Linux containers**。需要 Docker Engine 28+、Compose v2.26+；建议至少预留 4 GB 内存和 8 GB 磁盘。使用本机目录或 WSL2，避免网络共享目录。
2. 将完整仓库放在本机，例如 `C:\work\carbentra-campus-platform`。在该目录打开 PowerShell；首次构建需要访问镜像和依赖源，本机 8080 端口应空闲。
3. 运行启动脚本：

   ```powershell
   cd C:\work\carbentra-campus-platform
   .\tools\start-dev.ps1
   ```

   如果本机策略不允许运行 PowerShell 脚本，无需改变执行策略，可直接运行等价命令：

   ```powershell
   docker version
   docker compose version
   docker compose -f compose.yaml config --quiet
   docker compose -f compose.yaml up --build -d --wait --wait-timeout 600
   ```

4. 等待镜像构建、数据库迁移和首次样例导入完成，再打开 [本机工作空间](http://localhost:8080)。不要把首次下载或导入尚未完成当成登录故障。
5. 使用 `admin` / `development-only` 登录。这是虚构的开发身份，不对应真实校园人员。另有 `operator`、`analyst`、`viewer`，密码同为 `development-only`，可退出登录后比较权限。
6. 打开「系统管理」，检查数据库、后台任务和来源状态，确认「现场实际控制已关闭」。顶栏的「实时连接」只表示浏览器事件连接正常，设备是否新鲜仍以观测时间和质量为准。

启动异常时，在仓库根目录检查：

```powershell
docker compose ps -a
docker compose logs --tail 100 migrate api worker db web
Invoke-WebRequest -UseBasicParsing http://localhost:8080/health/ready
```

`migrate` 是一次性任务，成功后退出 0 是正常状态。它失败时先检查迁移日志，不要绕过迁移强行启动 API。Linux/macOS 同样使用 PowerShell 7 的 `pwsh -File tools/start-dev.ps1`。

开发服务只绑定 `127.0.0.1:8080`，不要将样例账户环境暴露到校园网或公网。`docker compose down` 保留数据库卷；**不要把 `docker compose down -v` 当作普通重启命令**，它会删除数据。备份、恢复、生产 HTTPS 和独立生产配置见 [运行手册](OPERATIONS.md)。Windows 脚本是否实际执行通过，以 [Docker 验证记录](DOCKER_VERIFICATION.md) 为准。

## 2 第一次浏览建议

按下面顺序走一遍即可理解主要工作流：

1. **运行总览**：先看顶栏「当前范围」，再看数据来源、最近观测和覆盖率。切换校区后，各业务页面沿用当前校区范围。
2. **校园空间**：从目录或二维地图选楼栋，切换三维，再进入有已发布图面的楼层和房间。通过「查看楼栋设备」或房间里的设备进入详情。
3. **设备与边缘**：查看「实时状态」「遥测证据」，比较观测时间与平台接收时间。不要先用控制按钮判断设备是否正常。
4. **能耗分析**和**碳与成本**：选同一楼栋和时间段，核对已知电量、覆盖率、因子和电价版本。
5. **预测与策略**：先阅读预测证据；需要练习控制时，再创建影子策略、评估、审批，并单独申请模拟调度。
6. **命令追踪**：打开返回的命令，等到明确的终态并查看阶段证据。受理提示不是执行完成。
7. **报表与审计**：生成快照并导出 JSON 或 CSV，复核来源、参数和生成时间。需要记录异常或空间安排时，使用「告警工单」「空间计划与检修」。

顶部搜索按钮或 `Ctrl+K` 可查找页面、楼栋和设备；按 `Esc` 关闭。浅色/深色主题在右上角切换。移动端用菜单按钮展开导航。

普通统计时间和计划时间按当前浏览器时区显示，提交 API 时转成 UTC；排放因子和电价版本表单中的生效/截止时间明确按 **UTC** 输入。电价每日峰谷时段另按该版本的 **IANA 日历时区**解释，不要混淆这三处时间。

## 3 先读懂来源与权限

### 来源标签

| 标签 | 可以怎样理解 |
| --- | --- |
| `SIMULATED` 模拟数据 | 软件生成的设备、观测或参数，用于演示和测试，不是实际用电 |
| `REPLAYED` 历史回放 | 回放数据；不能据此声称设备当前在线或授权现场动作 |
| `REAL` 真实接入 | 登记的真实来源模式；仍须分别检查身份、质量、校准和投运证据 |
| `REFERENCE` 参考 | 空间、计划或产品工程资料，不是实时遥测或实际占用 |

`—`、未知、数据不足、已过期、覆盖不完整都应保留原意，不能按 0、无人、无风险或已成功解释。`MIXED` 表示结果涉及混合来源，需查看来源明细。真实空间背景也不会把其上的模拟设备变成真实设备。

Sense B 的光照为未标定的 `raw_count`，不是 lux；没有 PIR、温湿度或电池续航能力。其 BLE 广播只作未认证诊断，认证 GATT 需要运营方逐设备密钥。XM125 的指定厂商 I2C 应用还需独立授权获取和烧录；固件构建/软件桥并不证明实际 RF 或教室覆盖。

Switch 的 `relay.1`–`relay.3` 独立寻址，但只提供一个 `meter.aggregate` 合计计量边界，不可复制为三份单路电量。软件输出回执不是触点或灯具的独立回读；MQTT PUBACK 更只是传输交付。

### 角色分工

| 角色 | 日常用途与写入权限 |
| --- | --- |
| `viewer` 只读访客 | 浏览授权范围的数据、已有报告与记录 |
| `analyst` 能碳分析员 | 创建和评估影子策略、生成报告；不能下发命令或审批策略 |
| `operator` 运维操作员 | 维护设备、绑定、回路、计划和告警；提交允许的命令、调度已批准评估 |
| `admin` 平台管理员 | 以上能力，以及策略审批和授权范围内的账户管理 |

全局因子、电价和时效设置需要**全局管理员**。角色之外还有校区范围限制：「全部可访问校区」不是全校无限权限。服务端对单项详情、历史、导出和实时事件同样检查范围；改角色、校区权限、启停状态或重置密码后，原会话会失效。生产账户在「系统管理」按实际职责和校区创建，不沿用开发身份。

## 4 校园空间与设备绑定

当前固定空间包包含 3 个来源校区、136 个建筑登记项和 603 个空间单元，其中 129 个建筑有地图模型。当前 v3 开发种子在这些空间上生成 603 个教室场景、4,221 个能力通道，全部保留 `SIMULATED` 来源。前一组数字是**来源资产覆盖**，后一组是**所选种子与空间包版本的演示规模**；教室场景名称不证明这些空间已被实地确认用途或安装设备，通道数也不是设备数。生产不自动生成这套样例。

旧版模拟计量边界不能直接补入新增教室负载。若新版种子提示需要全新开发数据库，应保留旧库与备份，使用独立命名、可丢弃的开发项目；不要更改种子标记、重写旧观测或重置真实运营数据库。步骤见 [运行手册](OPERATIONS.md)。

在「校园空间」选择楼栋后，下方显示参考楼层和空间；选择楼层图中的房间或空间清单可打开关联设备。没有图面的楼层仍可用清单导航。部分来源建筑没有可配准的室外几何，不会为了补齐地图而自动画出位置。

- 室外二维/三维用于按稳定建筑 ID 定位；二维中的「道路 · 绿地 · 水系」开关控制参考背景，不影响楼栋选择。这些背景不是电气或设备对象
- 楼层图是独立室内示意坐标，未与室外精确配准；高度可能含推断，模型不是实测 BIM
- 占用观测没有证据时显示未知。没有课程、计划人数为 0、房间颜色或三维模型都不能证明无人
- 背景或三维资源加载失败时，按提示重试或使用二维/目录继续；不要将资源失败解释为该楼没有设备

### 三种关系要分别维护

**设备身份**回答“是哪台设备”，使用稳定 ID；改显示名称不改身份。**空间绑定**回答“放在哪里”，按校区、建筑、楼层、房间记录。**电气回路**回答“由哪里供电、哪块表覆盖哪些负载”，在「配电拓扑」管理父子关系和计量边界。

移动设备时，进入设备详情的「空间绑定」，核对空间和实际回路，填写原因后确认变更。系统保留旧绑定的时间历史，并清除投运/控制授权；昨天的电量不会被改归到新房间。同房间不一定同回路，相邻楼栋也不保证独立供电。有计量历史的电路不能通过随意改父级重写历史边界。

新登记设备默认未投运、未获控制授权。练习模拟执行时，仅对明确的 `SIMULATED` 设备在「设备设置」选择内置模拟执行器、完成模拟投运并允许模拟控制；同时保留关键负载保护。`MQTT 虚拟边缘` 需要另行配置的虚拟传输环境，单改下拉框不会建立连接。真实设备不能靠普通设置勾选解除物理控制边界。

### 产品三维参考

Plug、Switch 与 Sense 的「产品参考」按产品家族分别展示固定版本的硬件发布资料。点击「加载三维参考模型」才下载可选模型，通过 SHA-256 校验后显示；可选中/聚焦零件、单独显示零件、自动旋转和卸载模型，并查看稳定零件 ID 与来源哈希。产品资料不会为每台设备重复加载实例，也不能证明该点位已安装相同型号、完成标定或可安全触碰。未发布模型时，遥测与业务功能仍可使用。

## 5 怎样解释能耗 碳 成本和预测

### 能耗分析

先固定校区、楼栋和时间段，再看「已知电量」及覆盖率。原始累计输入单位是 **Wh**；期间用电以有效累计差分换算为 **kWh**，不能把累计表读数逐行相加。瞬时功率 **W/kW** 与期间电量 **Wh/kWh** 也不能混用。

服务端排除跨启动、计数回退、绑定跨界、缺测及质量不合格区间，不会自动补齐未知耗电。有效区间少，已知电量仍可能有值，但代表的范围不完整。「计量平衡」分别比较父级、子级和差额；**不要再次把总表与其覆盖的分表相加**。残差不能直接当作偷电或已验证损耗结论。

### 碳与成本

- **位置法排放量**基于适用时段的排放因子与已知电量，不是已实现减排量。模拟因子、用电量和电价不能作为履约证明或真实账单
- **配置电量电费估算**仅计算配置的电量收费，不包括需量、容量、固定服务等另收费项。除了电量覆盖，还要看定价覆盖、未定价边界区间及警告
- 电价可以有基础单价和每日分时覆盖；未覆盖时段使用基础价。分时区间不可重叠，跨午夜拆成两行，结束可填 `24:00`
- 默认「严格定价」不会猜测跨不同费率计量区间的电量分配。主动选择「按区间时长分摊（估算）」后，按经过的 UTC 时长分摊已知 Wh；这不能恢复缺失的分时实测
- 电价时区的夏令时切换存在歧义等无法可靠解释的情况，会返回不可定价，不静默猜测

全局管理员通过「版本登记簿 → 登记版本」录入因子或电价的稳定 ID、版本、来源链接、来源模式以及有效起止时间。新版本保留历史引用；不要用覆盖旧版本的方式“修正”已生成报告。开发参数只是虚构假设，接入真实数据前应先核验适用范围和有效期。

### 负荷预测

在「预测与策略」查看预测曲线、上下界、观测新鲜度和计量设备覆盖，展开「模型选择与独立测试证据」。平台比较季节性基线与岭回归，按验证集选择模型，并另列独立测试的 MAE/RMSE；简单基线表现更好时仍选基线。

预测只代表合格历史设备队列的估计。部分设备被排除、样本不足或数据陈旧时，不应把曲线当成完整校园负荷。误差区间不是保证；合成数据上的模型表现不能写成真实校园 AI 精度或节能率。

## 6 从策略评估到模拟命令

策略工作流刻意分成三个动作：

1. **评估**：分析员或管理员创建影子策略，填写校区/楼栋、目标削减和候选上限，然后运行影子评估。检查候选设备、排除原因、预计削减功率和来源。评估只计算，不下发
2. **批准**：管理员核对这一次评估，填写审批说明，点击「批准影子策略」。批准只保留审核结论，不自动执行；重新评估后需要重新批准
3. **显式调度**：运维操作员或管理员在「单独授权模拟调度」中核对全部候选设备，填写原因并确认本次模拟削减，再点击下发。必须使用已批准的同一次评估，且距评估生成不到 5 分钟；过期后重新评估和审批

服务端在提交及实际领取执行任务时继续检查权限、时效、绑定、能力、关键负载、检修、本地故障和最小驻留等条件。因此刚通过的评估也可能在调度时被拒绝。没有合格候选或条件变化时保持零下发，不为达到百分比目标放宽保护。

单设备练习可用「命令追踪 → 申请模拟命令」，或设备详情的「控制申请」。选择保持、削减或恢复，填写原因与 1–60 秒有效期，可选择正常、边缘拒绝、执行失败、回执超时四种模拟场景。练习前先确认设备为新鲜、合格、已授权的模拟设备。

### 命令状态如何读

| API 状态 | 界面含义与操作判断 |
| --- | --- |
| `requested` | 已受理并持久化、待下发，还没有执行结果 |
| `dispatched` | 已下发，仍需关联回执和结果证据 |
| `acknowledged` | 已收到设备确认，尚不等于结果验证 |
| `acknowledged_unverified` | Switch 已报告软件动作，缺少独立物理反馈，不能称灯具状态已验证 |
| `verified` | 关联结果通过软件核对；模拟来源仍是模拟结果 |
| `rejected` | 条件或联锁拒绝，查看具体原因 |
| `failed` | 执行失败，查看阶段证据并处理原因 |
| `timed_out` | 在期限内未获足够反馈，结果不能当作成功或可靠取消 |

提交后点击「追踪此命令」，检查设备、动作、序号、到期时间和持久化状态轨迹。重复提交相同幂等请求会返回原记录；不要为了“变绿”连续新建命令。超时或交付不确定时先核对现有记录和设备观测，再决定下一步。MQTT 投递确认只证明消息投递，不证明输出改变；输出反馈也不代替现场隔离和验电。

## 7 告警 计划和报告

**告警工单**：按校区、楼栋、严重度和状态筛选，打开详情查看设备与处理时间线。运维人员可确认告警、补充处理说明、解决告警。确认表示有人接手，解决表示记录了处理结论，均不自动证明现场危险解除。

**空间计划与检修**：登记教学、活动、检修或节假日安排，填写范围、起止时间、来源和可选计划人数。支持编辑、批量 JSON 导入及带原因取消，取消后保留历史。批量格式见 [API 契约](API_CONTRACT.md)，一次最多 500 条。检修窗口参与控制闭锁，但不能替代挂牌、隔离或验电；无计划和计划人数 0 不能授权断电。

**报表与审计**：分析员或管理员点击生成报告，选能耗、碳核算、成本或运行类型，固定范围与时间；成本报告另选严格定价或显式分摊估算。生成后保存的是不可被后续实时数据覆盖的快照。详情可查看核算参数、完整内容，并导出 JSON/CSV；审计页可按实体查看谁在何时做了什么。

将报告交给他人前，先核对授权范围、来源模式、计量及定价覆盖、因子/电价版本。需要纳入迟到数据或新参数时，生成一份新快照并比较，保留旧报告以便复核。

## 8 接手开发时从哪里改

平台是模块化单体 API 加独立后台进程，不需要先拆成大量微服务。浏览器只访问同源 HTTP API；不要在前端接数据库或 MQTT。

默认 Docker 链路是：`web`（React 构建产物与 nginx）→ `api`（FastAPI）→ `db`（PostgreSQL/PostGIS），`worker` 共用持久化业务状态，独立 `analysis` 处理后台投影与预测；`migrate` 在 API 启动前一次性迁移。可选边缘服务通过受保护接口传送遥测与命令证据。详见 [架构说明](ARCHITECTURE.md)、[逻辑架构图](architecture/01_platform_logical_architecture.png) 和 [部署及仓库分工图](architecture/02_docker_deployment_repo_ownership.png)。

### 五仓库只保留各自的一份主源

| 仓库 | 应在这里修改 | 交接方式 |
| --- | --- | --- |
| `carbentra-campus-platform` | 云端/界面、教室状态与联动、身份/绑定、核算/预测/控制；唯一共享 Edge 与 IoT 应用合同 | 统一 API、`packages/iot-contract`、`edge/`、迁移与 Docker 交付 |
| `carbentra-smart-plug` | Plug 硬件、固件、具体线协议、本地保护与工程资产 | 发布版本化线协议、观测/反馈及源哈希；Edge 使用对应适配器 |
| `carbentra-presence-sensor` | Sense B 低压 USB-C 5V、XM125 I2C、raw 光照的硬件与固件 | 诊断广播/认证 GATT 与工程资产；没有 PIR 或电池续航方案 |
| `carbentra-smart-switch` | 三路普通照明开关硬件、固件、本地按键/保护与合计计量 | 三路具体命令/软件回执与单份 aggregate 计量；无独立触点反馈 |
| `njupt-map` | 空间身份、几何、地图与三维资产创作 | 发布 runtime 包；平台导入并保留稳定 ID、坐标和出处 |

平台 `packages/iot-contract` 是能力、事件、命令与具体校验的唯一维护位置，`edge/` 是唯一现役多设备网关。硬件仓库原来的 Plug Edge 只作溯源/交接参考，不与新网关并行运行，也不再同步成第二套可编辑合同。硬件固件保留其具体线格式；统一应用合同不意味着三个产品能执行相同动作。

`njupt-search` 是空间语义和界面参考；本平台是独立实现，不是对不可见原软件源码的覆盖。生成副本不要手改成另一套主源。

- **页面和交互**：`frontend/src/pages/`、`components/`；请求与权限在 `lib/`。从 `frontend/` 运行 `npm ci`，用 `npm run dev` 开发。Vite 默认代理本机 `127.0.0.1:8000`，先按后端说明启动 API；默认 Docker 不对外开放此端口。提交前至少执行 `npm test`、`npm run build` 和 `npm run format:check`
- **业务和数据库**：`backend/app/`，其中 `registry.py` 管绑定/回路，`telemetry.py` 管入库，`accounting.py`/`pricing.py` 管核算，`forecasting.py` 管预测，`control.py`/`adapter.py` 管命令，`scheduling.py` 管计划。数据结构变化增加 Alembic 迁移；测试和启动细节见 [后端说明](../backend/README.md)
- **HTTP 契约**：先对齐 [API 说明](API_CONTRACT.md)、后端请求/响应类型与 [OpenAPI](../packages/contracts/openapi.json)，再改调用方。鉴权、CSRF、校区范围和未知值语义不能只靠界面实现
- **IoT 合同与线协议变化**：应用语义、能力/单位、事件/命令 schema 和具体校验在 `packages/iot-contract` 维护；硬件线格式变化须与对应固件及 `edge/` 具体适配器一同版本化。按 [共享合同](../packages/iot-contract/README.md) 运行 `python packages/iot-contract/tools/check_contract.py`，并复验固件实际编码、Edge 与后端端到端路径。API 和 Edge 使用同一份合同；生成的 OpenAPI/类型不能反过来成为第二主源
- **地图变化**：在地图仓库发布，按 [空间包说明](../packages/spatial/README.md) 导入到独立暂存目录并验证哈希、ID 和绑定影响，再协调数据库导入。替换静态包本身不会更新既有数据库；未匹配来源保持未匹配

Docker 中前端改动需要重新构建 `web`；可用 `compose.dev.yaml` 开启后端热重载。SQLite 只用于明确的本地开发/小型测试，部署与迁移验证使用 PostgreSQL。完整验收、真实进程、MQTT 虚拟链路及浏览器运行方式见 [验收说明](../tests/acceptance/README.md)；不要把依赖安装、编译或 Compose 配置解析当成运行验收。

## 9 从本机样例走向真实接入

先接入只读测量，确认数据可信，再单独讨论现场控制。不要在演示 Compose 上打开物理开关试设备。

1. 按 [运行手册](OPERATIONS.md) 使用独立生产配置，配置机构 HTTPS、秘密文件、真实管理员和备份恢复。生产不自动导入样例账户与设备；明确选择授权空间包和参数版本
2. 在硬件仓库完成对应修订的安全、计量、负载适配与现场安装审查；保留实际报告编号。这里的引用字段只记录人工审核资料，不替代试验或认证
3. 登记稳定真实设备 ID、实际负载 ID/名称、能力、当前空间和回路。由操作人员配置设备身份、证书、精确主题 ACL、边缘与平台设备允许列表；秘密材料留在批准的秘密存储中
4. 在控制关闭状态验证重启纪元/序号、原始 Wh、观测与接收时间、去重、断网重传、质量和新鲜度。`REAL` 标签本身不能使无效时间、缺测或未经标定的数据变可信
5. 只有经过单独授权的现场投运流程，才可处理部署开关、精确 release ID、设备级放行和边缘独立门禁。登记投运证据并不会启用控制；重新绑定或撤销放行会使后续控制失效
6. 若未来确实放行物理动作，操作前须明确核对设备、实际负载、动作和市电后果；提交和领取任务时仍重查联锁。关键负载、通信不确定和现场隔离由合格人员按现场规程处理

当前没有网页投运/放行管理表单；相关 API 是独立操作人员流程，见 [API 契约](API_CONTRACT.md)。设备详情已有面向未来合格单设备的具名负载/动作后果确认，但交付环境仍闭锁，策略批量调度仍只用于模拟设备。

交接本身没有完成这些现场步骤，也不包含任何真实继电器动作。校方数据使用、地图/室内资料和硬件显示资产的对外发布权限也需先核对，见 [第三方说明](../THIRD_PARTY_NOTICES.md)。

## 10 验收与日常排障入口

以记录中的**对应源码/镜像版本、实际执行环境和通过/失败/未执行状态**判断覆盖范围，不照抄会变化的测试数量：

- [Docker 验证记录](DOCKER_VERIFICATION.md)：实际容器、健康状态、持久化、恢复与浏览器检查，以及环境限制；其中仍标为进行中或待验证的条目不是通过
- [本次本机验证记录](DOCKER_VERIFICATION.md) 与 [验收运行说明](../tests/acceptance/README.md)：复现入口、实际结果和各自测试范围
- [持续验证说明](CONTINUOUS_VERIFICATION.md)：CI 配置的覆盖边界；有工作流文件不代表远端已推送或 GitHub 已执行

最小交接自查：能登录；校区范围正确；未知/过期/模拟标识保留；能从楼栋定位设备；核算口径和覆盖率可解释；模拟命令有明确终态；报告可导出；重启与恢复结果有对应证据；物理执行仍关闭。

常见情况：

- **按钮不出现或 403**：先检查角色和校区范围，权限以服务端结果为准
- **有页面但数据不更新**：检查浏览器连接、API、worker 心跳和最近观测；轮询可补充事件连接，不能补造设备观测
- **不能控制或没有候选设备**：阅读闭锁/排除原因，检查模拟来源、投运、授权、关键负载、维护窗口和新鲜度，不延长安全期限掩盖问题
- **费用或预测不可用**：先缩小范围，检查数据/定价覆盖、版本有效期、时区与质量；不可用不等于 0
- **三维模型或背景不可用**：检查已发布 manifest 和资源状态，先用目录或二维继续，不能据此伪造模型或安装状态
- **启动或升级失败**：保留卷和日志，按 [运行手册](OPERATIONS.md) 检查迁移、健康与回滚；不要直接清空数据库重来
